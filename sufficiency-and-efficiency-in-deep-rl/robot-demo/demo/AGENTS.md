# demo specification 

## abstract 

This document is a software specification. 
It is meant to be read by the agent (you) which'll write the initial draft of this demo. 
This demo will illustrate the advantages of approximate sufficient statistics applied to deep reinforcement learning (RL) in robotics. 
Since data is integrated into the sufficient statistic with optimal statistical efficiency, 
there an increased cost to cover any single observation, 
but the entire dataset never need be entirely reprocessed, 
ultimately saving processing time. 
This is possible through a rigorous underlying model which carries all information forward, 
utilizing transforms at least-approximately equal to change of measure. 
The key value illustrated by this demo: 
when starting with a rich base model, 
deep RL robotics can learn very efficiently from new data. 

The demo uses a PiCar-V Raspberry Pi robot controlled by a server with a single GPU. 
The initial model will be a `Qwen 2.5-VL-3B`, a small vision language model (VLM). 
The model will be guided verbally by the experimenter to learn and perform a series of tasks. 
Initially, the model will control the robot with agentic commands, 
but eventually the model will be fine-tuned to perform commands with a value function instead of agentic commands. 
This will illustrate a robot learning a task efficiently.

## what is in the `demo/src/core` directory 

1. `core/ssr_agent.py` is the foundational abstraction layer of this demo: the `SSRAgent` class. 
It leverages a low-dimensional Hessian estimates to produce natural gradients. 
The big trick: the Hessian is calculated as a sufficient statistic, enabling online learning - even if integrating individual samples takes longer per sample, it'll produce accurate Hessian estimates faster for large sample sizes. 
Another trick: since this is RL software, we'll move our Hessian estimate over the statistical manifold by also keeping moving average Amari-Chentsov tensors (work-in-progress for me, not you). 
How to use this software: simply (A) define your model as a concretization of this class, (B) implement the `loss` function, and (C) choose an optimizer without momentum because the Hessian already provides natural gradients. 
Note that `loss` must be mean-scaled, not sum-scaled. 
Further note: optimization and Hessian calculation only occurs for parameters with `requires_grad is True` - no need to waste a massive Hessian on unused parameters. 
2. `core/lanczos.py` is my numerical methods package, implementing variants of the Lanczos algorithm. 
The Lanczos algorithm is oddly perfect for this application, efficiently providing a low-rank Hessian estimate. 
Numerical instability due to near-singularity is not a concern here; our Hessians are simply too large. 
3. `core/replay_buffer.py` is a simple RL replay buffer. 

## model design 

The model (a PyTorch `nn.module`) will concretize the `SSRAgent` class. 
It will leverage a `qwen2.5-vl-3b` VLM sub-module as a foundational model. 

While fine tuning will be applied, it'll be via low-rank adaptation (LoRA). 
LoRA will not be applied to the visual encoder, just the transformer backbone and head. 
LoRA values will be initialized to zero. 
The underlying VLM is never to be modified because it will be used to evaluate the performance of the tuned model. 
Use `.requires_grad=True` to control which parameters are tunable. 

An additional head will be added to the VLM, encoding a value function. 
The value head's parameters are tunable, of course. 
Actions are:
1. `drive-left` 
2. `drive-right` 
3. `drive-forward` 
4. `drive-backward` 
5. `look-left` 
6. `look-right` 
7. `look-up` 
8. `look-forward` 

Despite having finite actions, the linearly-combined action vectors are continuous. 
So, we'll use an Actor-Critic model. 

Since we need to fine-tune our model away from agentic commands, 
we'll create an action vector space and linearly combine actions continuously according to some `t` between 0 and 1. 
At `t=0`, all actions are purely agentic. 
At `t=1`, all actions occur entirely due the value head. 
For `t` between 0 and 1, the agentic action `action_agentic` and value action `action_value` will be represented as vectors and combined as `(1-t)*action_agentic + t*action_value`. 
Training starts from the base VLM with `t=0`, then `t` is gradually increased as data is continually generated until the robot no-longer needs to generate text. 
The `action_value` should be produced before any text generation occurs, 
thereby producing a computational savings when `t=1`. 

The loss function is a sum of two parts:
1. **VLM loss**: this reuses the existing VLM loss function. 
2. **RL loss**: this is an Actor-Critic loss. 
This keeps agent's visual processing & text generation functional while still learning to play the RL game. 

## experimental design 

Experimental phases:
1. Collect initializing data: Keeping `t=0`, collect a large amount of data to populate an initial sufficient statistic estimate. Data volume must be large enough that this estimate is accurate. 
2. Policy tuning: Sample observations while tuning the model. Allow `t` to traverse continuously and slowly from 0 to 1. In theory, this should train the agent to efficiently drop its agentic interface and rely entirely on its policy interface. 
3. Retasking: Keeping `t=1`, allow tuning to proceed. At game start, user selects a reward prompt (default is "find the red ball"). Swapping between games allows experimental assessment of (A) resistance to catastrophic forgetting, and (2) speed to retask. 

Two essential experimental modules are needed:
1. **Experimental software**: `src/experiments/experiment_interface.py` will be the primary experiment interface. All experiments can be run with this script. It runs the PiCar via `PiCarGymEnv` game iterations. More requirements: 
   1. Allow the user to optionally specify a `fixed_t` value for the environment. Otherwise, allow `t` to traverse from 0 to 1. If `t` is traversing, print updated values for the user's viewing as the game progresses. 
   2. Allow the user to optionally load a model from a directory path, otherwise load the default VLM with zeroed-initialized LoRA parameters. 
   3. Create a `uuid` name for the experiment instance and print it to screen at game start. 
   4. Create a directory in `data/[uuid]` named after the experiment instance. Write all new observations in this directory. Don't count on the `replay_buffer` to store or index observations, because every `SSRAgent.memorize` call is paired with a `ReplayBuffer.clear` call. Frequent writing is important because experiments are likely to halt suddenly due to PiCar Raspberry Pi crashes due to low batteries. 
   5. Create a directy in `model/[uuid]` named after the experiment instance. Use it to store model snapshots. Only store tunable parameters; it's very wasteful to store untuned VLM copies. 
   6. Run until user hits `Ctrl-C`. 
2. **README**: `src/experiments/README.md` how to use the experimental interface, including the experimental phases above. For each phase, an example Bash command must be shown. 

## requirements 

1. **TTS and STT**: Write a Python interface for text-to-speech (TTS) and speech-to-text (STT). 
This interface will allow the user to converse with the robot. 
The TTS model `Piper`. 
The STT model is `whisper-large-v3-turbo-int8`. 
Use model files if they are already available on disk. 
If models are not in the `demo/model` directory, then download them. 
Remember to download large model files into the `demo/model` directory. 
Be sure to follow [`model/README.md`](model/README.md) instructions. 
2. **Model**: Implement a model as specified in the `Model Design` section above. 
Use `demo/src/model` directory to store model code. 
Use model files if they are already available on disk.
If models are not in the `demo/model` directory, then download them. 
Remember to download large model files into the `demo/model` directory.
Be sure to follow [`model/README.md`](model/README.md) instructions. 
3. **RL env**: Write an RL environment for the PiCar in `src/env`.   
Its interface should be similar to OpenAI Gym.
It will leverage the `picar-v-rl-env` interface for controlling the robot.
The user will direct you to a local copy of `picar-v-rl-env` for your review.
The game loop involves:
   1. listen for any text from the user, generated via STT;           
   2. collect an image from the robot's camera;
   3. use the underlying VLM model on the image to produce a reward score;
   3. format history, image information, reward data, and input from the user into a `messages` object according to [this documentation](https://huggingface.co/docs/transformers/en/model_doc/qwen2_5_vl);
   4. pass `messages` into the model and get an action vector in-return;
   5. if the robot has produced a text, share it with the user via TTS;
   6. pass the action vector to the robot for exection.
Every `K` (tunable) game iterations, the model is tuned to data in the replay buffer. 
The game ends the user hits `Ctrl-C`.
End the game by
   1. ensuring all history has been saved to disk in the `demo/data` directory; and 
   2. a snapshot of the tuned LoRA and action head parameters are written to disk. 
Be sure to follow [`data/README.md`](data/README.md) instructions.
4. **Unit and integration tests**: While implementing the prior requirements, 
the user should prompt you to add tests whenever needed. 
Unit tests should be fast (entirely running in under 1 min) and used to protect already-implemented feature from active development. 
Integration tests are slow and may require the user manually setup the robot. 
An integration test battery can take up to 10 min but shouldn't involve extensive user involvement - ideally, the user merely sets up the robot for testing. 
5. **Experimental software**: populate `src/experiments` according to the `experimental design` section above.
